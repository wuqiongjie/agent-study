# 04 · 前端工程师的差异化能力

Agent 的能力上限由模型决定，但**可用性**几乎由前端决定。下面三件事是后端不擅长、而前端必须扛起来的。

## 一、流式与可中断

- **首字节延迟**是被感知的响应速度，必须流式，不能等完整响应。
- 长任务要能**暂停 / 取消 / 续接**，而不是一个转圈。
- 中断请求要真的 `abort`，不只是 UI 上不渲染 —— 否则后台继续烧 token。
- 区分「连接中 / 思考中 / 调用工具中 / 生成中」四种状态，用不同 UI 表达。

## 二、工具调用可视化

把 Agent 的「思考过程」变成可折叠的时间线：

```
▾ 共 4 步 · 12.3s · 8,412 tokens
  ▾ 调用 web_search("LangGraph interrupt 用法")      0.8s
  ▾ 调用 fetch_url(...)                             2.1s
  ▾ 撰写报告                                        9.4s
```

- 每个工具折叠卡片展示：入参、耗时、返回摘要（不要展示完整原始 JSON）。
- 失败步骤标红并支持重试。
- **用户信任度的差距，主要来自这里。**

## 三、成本与延迟控制

前端能做的：

| 手段 | 效果 |
| --- | --- |
| 请求去重与缓存 | 相同输入不重复付费 |
| 减少无效请求（防抖、意图确认） | 直接省钱 |
| 并发编排（无关工具并行） | 显著降延迟 |
| 历史消息折叠/懒加载 | 降低长会话渲染压力 |
| 展示 token 与费用 | 让用户有感知、也让评审有数据 |

## 四、面试 / 评审的加分点

1. 能说清「为什么 Agent UI 必须用流式 + RSC，而不是 REST + setInterval 轮询」。
2. 能解释「工具结果为什么要压缩后再回传模型」（上下文窗口与注意力稀释）。
3. 能设计「人在回路」的交互协议，而不是只会调 API。
4. 有 trace 驱动 debug 的意识：先看到底调用了哪些工具、传了什么参数，再下结论。
5. 能量化：首字节延迟、完成耗时、token 消耗、失败率。

## 五、常见坑位清单（边做边补充）

- [ ] 流式响应被 Next.js 默认缓冲 → 需正确配置 streaming
- [ ] `useChat` 在工具调用时 UI 卡在旧状态 → 需区分 tool-invocation 状态机
- [ ] 长文本打字机导致重排卡顿 → 需 `useMemo` / 虚拟化 / CSS `contain`
- [ ] Markdown + 代码高亮在流式中途渲染炸裂 → 需防抖渲染或增量解析
- [ ] 移动端输入框被键盘顶掉
